# Phase 5 多用户 — 盲区报告(blindspot-pass)

*2026-07-10 · 范围:认证 → 服务端权威 → 实时同步(Yjs/Loro)评估 → 评审工作流 ·
约束 #0:单用户模式不降级(离线单文件 + 本地免登录默认;认证为部署开关)· 输出 = 供用户反应的报告,不实施*

## 领地实况(读代码所得,非读文档)

| 事实 | 位置 | 多用户含义 |
|---|---|---|
| 审计 actor = `getpass.getuser()` + 引擎版本 | `backend/store.py:104` | 服务器模式下所有人都是同一个 OS 用户 —— 证据链的"谁"失效 |
| CORS `allow_origins=["*"]` | `backend/app.py:18` | localhost 无害;共享服务器上 = 任意网页可打 API |
| **存档静默回退 localStorage** | `frontend/src/api.ts`(/api/saved 全家 catch → `lsSave`,旗标"离线存档") | **地雷**:开认证后 401 会被当作"后端不可达",用户的保存悄悄写进浏览器,以为存到了服务器 |
| 保存 = 整载荷按 sid 覆盖(LWW) | `POST /api/saved` | 两人同项目并行保存 → 工作区头互相覆灭;但双写版本库**内容寻址保留双方版本**(可恢复,不可见) |
| 单进程 uvicorn + SQLite WAL | `Makefile:51` | 单写者模型;小团队单进程可行,多 worker/多写需决策(SQLite 串行化 vs Postgres) |
| ai_drafts / cases / versions 无用户身份列 | `store.py` 表结构 | 采纳 AI 草案、贝叶斯升 A 级的"经手人"未记录 —— 监管会问 |
| undo 历史在客户端 store | `stores/projectStore.ts` | 共享项目模型下天然安全;并发编辑模型下需重新设计 |

## ① 请求默默做出的假设(各自在哪里会断)

- **A1「多用户 = 并发编辑」**:序列里的 Yjs/Loro 步隐含此意。若真实需求是"共享项目 + 评审工作流",
  CRDT 整层可删——架构量级差一个数量级。*断点:需求本身。*
- **A2「先建认证层」**:身份提供方未定(企业 AD/LDAP/SSO?本地账户?共享令牌?),选型决定整个栈;
  先写本地账户可能全部返工。*断点:部署环境。*
- **A3「现保存模型可承载多用户」**:LWW 整载荷覆盖 + 静默 localStorage 回退,两者都必须变——
  前者要锁或合并,后者在认证模式必须显式失败而非降级。*断点:api.ts 回退逻辑与 /api/saved 语义。*
- **A4「部署是我们控制的共享服务器」**:内网?云?隔离网?决定 TLS/备份/密钥(ANTHROPIC_API_KEY
  服务端持有)方案。*断点:运维归属。*
- **A5「单用户退化免费」**:架构上基本真(叠加层),但客户端行为必须感知模式(回退地雷即证)。
- **A6「SQLite 继续够用」**:单进程 ~10 用户可辩护;并发写压力与备份策略需数据决策。

## ② 已知未知 → 访谈问题(按 答案改变设计的概率 × 猜错代价 排序)

1. **Q1 协作语义(定架构量级)**:同一 ETA 需要多人**同时**编辑(Google-Docs 式,CRDT)?
   还是**共享项目 + 串行编辑 + 评审流**(check-out/评论/签发)就满足?——监管场景通常后者足够;
   RiskSpectrum 团队版也是库锁模型。答案直接决定 Yjs/Loro 是否出现在 Phase 5。
2. **Q2 部署与身份**:服务器落在哪(公司内网/云/隔离网)?身份接谁(AD/LDAP/OIDC-SSO/本地账户)?
   ——决定认证栈与密钥/TLS/备份形态。
3. **Q3 用户群与角色**:几个人?角色集(分析员/评审人/只读查阅——监管方要不要直接给只读)?
   项目按组隔离还是全组织共享?
4. **Q4 评审语义(证据链延伸)**:「评审」具体指什么——版本冻结+电子签发(签名进报告页脚)?
   逐元素评论线程?报告导出前的审批门?尤其:**AI 草案采纳与贝叶斯升 A 级的"经手人"**要不要
   成为审计一等公民(现在只有 OS 用户名)?
5. **Q5 并发写短期策略**:在 CRDT 之前,项目级 check-out 锁(RS 习惯)vs 乐观保存+冲突提示
   (版本库已保底不丢数据)——哪个符合团队工作习惯?
6. **Q6 运维**:谁装谁管?升级/备份/停机窗口约束?

## ③ 未知的已知 → 用工件让用户"见了就认"

- **评审/签发 UX**:与其抽象问 Q4,不如 `design-directions` 出 3-4 个单文件 mockup
  (a. 版本冻结+签章页;b. PR 式评论线程;c. 台账内签发列 + 报告页脚签名;d. 审批门看板)。
- **锁模型手感**:`reference-hunt` RiskSpectrum 多用户/数据库版的 check-out/check-in 行为
  ——用户有 RS 肌肉记忆,对齐或明确偏离都要有意识。
- **登录/角色管理面**:一页 mockup 即可暴露"要不要自助建账户/改密码/停用"。

## ④ 值得先跑的风险探针(便宜,回收大)

- **P1 双客户端覆灭演示**(半小时):两个 TestClient 交替 POST 同 sid → 证实工作区头 LWW 覆灭 +
  版本库双方版本俱在 → 给 Q5 提供事实底座("不丢数据,但会互相看不见")。
- **P2 认证地雷复现**(半小时):给 /api/saved 挂一个返回 401 的桩 → 证实前端静默转"离线存档"
  → 结论:认证模式必须区分"网络不可达"与"未授权",后者显式报错。**无论 Phase 5 走哪条路,
  这个修复都要做。**
- **P3 SQLite 并发写微基准**(1 小时):线程池并发 create_version/audit 写 WAL 库,测锁等待
  → SQLite-单进程 vs Postgres 决策的数据。
- **P4 Yjs/Loro 试针 — 仅当 Q1 答"并发编辑"才跑**:EventTreeModel 绑 Y.Doc,量文档膨胀与
  合并语义(尤其 undo 与 CRDT 的相互作用);否则整个不碰。
- **P5 服务器姿态清单**(半小时):CORS 收紧、错误文本泄漏、限流、TLS 终结点——server 模式检查单。

## PSA 清单扫描(逐项)

- **证据链**:核心暴露面。actor 必须在 server 模式成为认证身份;签发/采纳类动作(报告导出、
  AI 应用、贝叶斯升级)的"谁"要进只增审计与报告页脚。单位/口径/独立性/保守方向:本阶段不触碰
  量化语义,无暴露。**契约稳定**:/api/saved 形状、离线单文件、v2 载荷兼容全部不得破——认证
  必须走 header/cookie 叠加,不改载荷。
- **数值卫生**:不适用(无量化改动)。

## ⑤ 建议

**先访谈,后规格,探针并行。** 顺序:Q1(协作语义)→ Q2/Q3(部署/身份/角色)→ 以 mockup 问 Q4
(评审 UX)→ Q5/Q6。P1/P2 两个探针便宜且无论答案如何都有用,可在访谈期间跑掉;P4(CRDT 试针)
在 Q1 得到"需要并发编辑"之前**不投入**。我的倾向(供你反驳):监管场景 + 小团队 →
**共享项目 + check-out 锁 + 评审签发流**,把 CRDT 留作 Phase 6 选项——Phase 5 交付
认证开关、身份入审计、锁与冲突提示、评审/签发工作流四件事。
